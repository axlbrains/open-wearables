## CI / local dev

- `ci.yml` triggers **only on push to `main` and on pull_request** (paths-filtered). **Pushing to `axl-integration` does NOT run CI** — open a PR to get tests. So local pushes to the integration branch are unvalidated.
- ⚠️ **`backend-code-quality` runs `ruff check` + `ruff format --check` + `ty check` over the WHOLE backend** — not just `app tests scripts`, and `ty` is not `mypy`: it ignores `# type: ignore[...]` and only honours `# ty: ignore[rule]`. Both gaps had been red since July/August and nobody saw it (see the CI note below). Two traps worth remembering: (1) `migrations/` is linted, and every `alembic merge` emits the template's unused `op`/`sa` imports — lint a new merge revision before its first commit, because once it is applied `scripts/check_migrations.py` compares its `down_revision` line verbatim and any reformatting (even a trailing `# fmt: skip`) reads as a re-point; the three already-applied merge revisions are frozen via ruff `exclude` in `backend/pyproject.toml`. (2) Our `get_redis_client()` must stay typed `redis.Redis`, **not `Any`** — with `Any` the checker cannot produce the errors upstream's `ty: ignore` comments suppress, so every one of them becomes an "unused suppression" warning in otherwise-pristine upstream files, and stripping them would re-conflict on every sync.
- ⚠️ **A PR from `axl-integration` into `main` does NOT run CI either**: the two branches have diverged far enough to conflict, and GitHub skips `pull_request` workflows when it cannot build the merge commit (the PR just shows no checks at all, not a failure). To get a real CI run, push the pre-work commit as a throwaway base branch and open the PR against **that** — a clean, mergeable diff. Used 2026-09-17 (PR #39 off `ci/base-pre-0.9-sync`).
- Backend tests need **Docker** (testcontainers spin up Postgres + Redis in `conftest.py`); they can't run in a Docker-less sandbox. CI provides Postgres as a service + env (`ENV=test`, `SECRET_KEY`, base64 `MASTER_KEY`).
- **The full suite runs locally on macOS since 2026-08-15** (`f0e3ea07`) — three fixes, don't regress them on upstream syncs: (1) celery `socket_keepalive_options` resolved via `socket` constants, not raw Linux ints (macOS `setsockopt` fails with "Protocol not available" — upstream #1357 hardcodes `{4:60,5:10,6:3}`); (2) conftest points the import-time celery app's broker/result backend at the test Redis container (it was baked from un-patched settings and only worked in CI where a real Redis listens on localhost:6379); (3) `test_redis_url` neutralizes our fork's `redis_url_override` conftest patch. Local runs work with `config/.env` present (conftest overrides win).
- No `uv` preinstalled in some envs: `pip install --user uv` then `uv sync`. To import the app / run non-DB tests locally set `ENV=test SECRET_KEY=… MASTER_KEY=<base64>`.

## "Someone else's no-data is not our error" — the recurring noise class

Three prod incidents in two days, all the same shape: a provider says "nothing here" in a way that looks like a failure, we report it, and a retry loop keeps re-reporting it forever.

- **Polar 401 on optional endpoints** (0.8.5): Elixir/SleepWise/daily-activity are gated per user, device and consent — one athlete 401s while another gets data on the same endpoint with a healthy token. `Polar247Data.CORE_ENDPOINT_PREFIXES` now draws the line at the product dependency: sleep (`/v3/users/sleep/`, trailing slash matters — `sleep-skin-temperature` is NOT core) and `/v3/exercises` stay loud, everything else logs `polar_endpoint_not_permitted` and returns no data. A dead token still screams, because it 401s on the core endpoints too. Took three deploys (0.8.3→0.8.5) because each wrong guess only showed up on a live sync, not in tests.
- **Strava 404 on `/streams`** (0.8.7): manual activities have no streams. `_ingest_workout_streams` now returns `None` for that — distinct from `0` ("streams exist but weren't ready"), so the webhook path also stops scheduling delayed retries for an activity that will never have samples. One hand-logged gym session was producing a traceback plus a Sentry event twice an hour, forever, because the 6h lookback re-covers it and the skip-if-samples-exist guard can never be satisfied.
- **Polar 404 on `/fit`** (0.9.4): phone-logged and manually entered exercises have no recorded file. The quiet branch shipped in 0.9.1 was **dead code** — `download_binary_content` surfaces the status through `response.raise_for_status()`, i.e. `httpx.HTTPStatusError`, while the branch caught fastapi's `HTTPException` (what the JSON paths raise). The test passed because it raised the wrong type too. Same trap applies to any provider path built on `download_binary_content`.
- **The noise was in `api_client`, not the providers (fixed 0.9.7).** `make_authenticated_request` logged at error level **before** raising, so a caller that already treats the status as "no data" could not suppress it — Polar's `_make_api_request` had returned `None` on 404 since forever and the error line was emitted anyway, ~130/day for one athlete, with **no endpoint in the payload** to tell which call it even was. Two fixes: (1) an empty body / 204 now returns `None` instead of being fed to `.json()` (that `JSONDecodeError` became an error log plus a bogus 500 — Polar answers "nothing new" that way on several endpoints); (2) a new `quiet_statuses=(...)` argument lets the caller name the statuses it expects and will handle, which skips the error log but still raises, so flow is unchanged. Polar passes `(401, 404)` for non-core endpoints only, so a core endpoint breaking stays loud. Both error logs now carry `endpoint` (and the status). **0.9.9 wired the Strava half**: `BaseWorkoutsTemplate._make_api_request` forwards `quiet_statuses` (keyword-only; the Hevy and Sensorbio overrides grew it too to stay substitutable) and Strava's `/streams` call passes `(404,)`. Until then the 0.8.7 "manual activity has no streams" fix was only half done — the flow was quiet but `api_client` still logged the 404 at error level first, which is exactly what the maintainer pointed at (`api_client.py:245 # this is the problem`) when closing the-momentum#1575. It only looked fixed because that activity had aged out of the 6h lookback.
- Rule of thumb when adding a provider path: before wrapping an exception in `log_and_capture_error`, ask whether that status can mean "this user/activity legitimately has no such data". If yes, it needs its own quiet branch — and **assert it with the exception the helper actually raises**, or the branch is decorative.

## ⚠️ Large SDK batches take a different code path (and it broke silently)

- The dispatcher offloads any payload over `task_payload_inline_max_bytes` (256 KB) to task-payload storage and swaps the task for its `*_reference` variant, forwarding **every other kwarg verbatim** — see `_OFFLOAD_MAP` in `task_dispatcher.py`. So a reference task's signature must stay a superset of its base task's.
- 2026-09-07 upstream added `payload_ref` to `process_sdk_upload`; the reference sibling wasn't updated, and **19 Apple SDK batches were accepted with 202 and then dropped** after Cloud Tasks exhausted 160 retries. Raw payload archival is off in prod (`raw_payload_storage=disabled`), so they were unrecoverable server-side — the data needs a re-export from the device. Fixed in 0.8.3, plus `TestReferenceTaskSignatureParity` so the drift fails in CI instead of in prod.
- **How to detect silent batch loss**: compare `apple_sdk_batch_received` (api) against `apple_sdk_import_complete` (worker) by `batch_id` over a window. Both carry `batch_id`, and a received batch with no completion never reached the worker. Healthy looks like 18 received / 18 imported.

## One live connection per provider account (fork divergence, 2026-09-08)

- `settings.single_active_connection_per_provider_account` (default **true** here): connecting a provider account to a profile revokes that same account's connections on every other profile, in both the OAuth (`BaseOAuthTemplate._revoke_superseded_connections`) and API-key (Hevy) flows, emitting `connection.revoked` with reason `superseded_by_new_connection`.
- Upstream instead treats a shared provider account as a feature and fans synced data out to every profile holding it (`sync_vendor_data_task`); set the flag false to get that back. That fan-out is what masked a real problem: one athlete had two OW profiles on the same Polar account, re-authorising killed the older token at Polar, and the stale row 401'd hourly with nothing to clear it.
- ⚠️ **`DELETE /users/{id}/connections/{provider}` calls the provider's deregistration API.** For Polar that is `DELETE /v3/users/{provider_user_id}`, which unregisters the *athlete*, not the connection — dangerous when two profiles share the account. When cleaning up a duplicate, change `status` directly instead. For Strava it is `POST /oauth/revoke` on that connection's own token, which is safe.
- ⚠️ **axl-api does not handle `connection.revoked`** (only `connection.created`), so disconnects don't reach it and its state drifts — tracked in [axl-api#297](https://github.com/axlbrains/axl-api/issues/297).

## Late-arriving provider data — the recurring race class

Two prod bugs of the same shape: data that becomes available *after* its dated sync window has passed is never fetched again.
- **Strava streams** (fixed 0.7.2): webhook precedes stream processing → delayed retry task; see Strava section above.
- **Polar sleep** (fixed 0.8.0, 2026-09-07): nights enter `/v3/users/sleep/available` only after the watch syncs with Polar Flow — days late for infrequent syncers. `get_sleep_data` intersected available nights with the hourly window, so late nights were lost (Jevgeni had zero polar sleep since June). Now it also fetches any available night within Polar's 28-day retention that isn't stored yet — existence probe `event_record_service.get_sleep_end_dates` filters by **`DataSource.provider`** (`source` is empty for pull-ingested polar rows — filtering on it re-fetched everything hourly and hit an FK violation on scores, 0.8.1). Both polar save paths now re-point the health score at the record `create_or_merge_sleep` actually returned (merge discards the pre-generated id).
- When adding a provider, ask: does the API list data by *availability* or by *date*? If availability lags, don't intersect with the sync window.

## Fork feature: Polar workouts come from the FIT file (card 279, 2026-09-17)

- Polar's `/v3/exercises` JSON carries **four** metrics — avg/max HR, calories, distance — and that is exactly what the athlete saw in the app. `/v3/exercises/{id}/samples` and `/heart-rate-zones` **404 on AccessLink**; `/fit`, `/gpx` and `/tcx` all return 200. So the watch's real recording (speed, cadence, power, altitude, GPS, temperature, laps) is only reachable through the FIT file.
- `PolarWorkouts._ingest_fit` downloads `/v3/exercises/{id}/fit` and runs it through the shared `app/services/fit_parser.py` (the same parser Garmin already used). The FIT **session** message is new: `parse_fit_file` now returns `result.session`, a rollup keyed by `EventRecordDetail` field names so it merges straight into a detail. **The JSON wins where the two overlap** — it is Polar's own rollup — and the FIT only fills what Polar left out. Laps land in `segments`, samples in `data_point_series` (gated by `INGEST_WORKOUT_SAMPLES`).
- ⚠️ **The skip must carry the stored FIT fields forward (fixed 0.9.6, shipped broken in 0.9.1).** `event_record_detail_repository.bulk_create` upserts **every** column, so a detail rebuilt from the JSON alone nulls out everything the FIT contributed — `moving_time_seconds` included, which is the marker the skip is based on. The guard therefore erased its own evidence and prod oscillated on a perfect hourly alternation: ingest, erase, re-download, erase — ~12 downloads/athlete/day, ~20k samples rewritten each time, and the workout showing its FIT metrics only half the time. `_carry_over_fit_fields` now copies them onto the fresh detail when the file is skipped. **General rule for this codebase: any "skip the expensive re-fetch" guard must also preserve what the skipped work had written, because detail upserts are full-row.**
- ⚠️ **Exercise times were `2 x utc_offset` in the future until 0.9.8.** Polar's JSON gives a naive LOCAL `start_time` plus `start_time_utc_offset` in minutes, so UTC is local MINUS the offset; `_extract_dates_with_offset` (upstream code, unmodified) added it. Four hours out in summer, ten for the athlete on UTC+5. The tell: a workout's own FIT samples, which carry true UTC timestamps, never fell inside its own window — Strava's do, because its `start_date` is already a UTC instant. The old tests asserted only the duration, never the resulting instant, which is why the sign survived. **Correcting the times needs `scripts/data_migrations/fix_polar_workout_utc_offset.py` to run WITH the code change**: `event_record` dedupes on `(data_source_id, start_datetime, end_datetime)`, NOT `external_id`, so an uncorrected row gets re-inserted as a second copy at the corrected time. Pause `open-wearables-prod-sync-all-users` across the deploy+migration to close the race. Prod run: 11 corrected, 5 already right (Polar reported offset 0), 29 outside Polar's retention — those stay wrong and cannot be re-synced either. Upstream candidate.
- **Re-fetch guard:** sync windows re-cover the same exercise hourly and the FIT is immutable, so `_stored_fit_detail` probes `workout_detail.moving_time_seconds` — every FIT session has `total_timer_time` and the Polar JSON has no equivalent, which makes it an exact "was this file already parsed" marker. Workouts imported before this shipped get enriched on their next re-cover, so no separate backfill is needed.
- **Altitude span and steps are derived (0.9.10).** Polar's FIT has altitude and cadence on every record but puts no min/max altitude and no step total in the session (checked on both a Vantage M and a Grit X2; neither writes power either — that one genuinely needs hardware). `fit_parser._fill_session_from_samples` fills `elev_low`/`elev_high` from the elevation samples and `steps_count` from cadence, **only where the session is silent**, so a device's own figure always wins. Steps: FIT cadence for on-foot sports counts one foot, so steps = 2 x cadence integrated over the real gap between samples, with gaps > 10 s treated as auto-pause and skipped; cycling gets no steps (pedal rpm). Validated on prod runs: stride 0.92-1.09 m against recorded distance. It is an estimate, not a pedometer count. Existing workouts were filled from their stored samples by `scripts/data_migrations/backfill_polar_fit_derived_fields.py` (only NULLs, idempotent, no Polar calls). Fork-only for now: upstream ingests no Polar FIT, and our `session` rollup is itself unmerged there.
- Two runs had watch-side GPS altitude garbage (yJbbY1Y4 2026-09-05, 02e6lpK3 2026-07-04; device ascent 308 m / 415 m): elev_low/elev_high/total_elevation_gain nulled and their 5 190 elevation samples deleted on 2026-09-19. The 20 Polar workouts that show up twice by `external_id` are the known second profile on the same Polar account (revoked connection, uncorrected times, no FIT) — not a sync bug.
- Per the "someone else's no-data is not our error" rule: a 204/404 on `/fit` (phone-logged or manually entered exercise) logs `polar_fit_absent` at info and keeps the JSON metrics. Download or parse failure never blocks the workout from saving.

## Health Connect workouts: what the SDK sends vs what we derive (0.9.11, OW #41)

- **Android SDK < 0.12.0 sends an exercise session with a `duration` and nothing else.** axl-app pinned Flutter plugin `open_wearables_health_sdk: 0.0.21`, which bundles Android SDK **v0.11.2**; plugin **0.0.22** is the first on v0.12.0, which adds `distance` (m, summed DistanceRecords in the window), `totalCalories` (kcal), `averageSpeed`/`maxSpeed`, HR, power and cadence as `values`. All of those names already map in `workout_statistics.py`. So the real fix for "no distance on a Fitbit run" is bumping the plugin in axl-app (axl-app#109), not server-side aggregation.
- Server side, 0.9.11: (1) `energy_burned` stays **null** when no energy statistic is sent (the importer used to start the sum at `Decimal("0")`, which stored a fake 0 kcal); (2) `moving_time_seconds` from Health Connect `segments` (`app/services/sdk/workout_segments.py`, `health_connect` provider only — Apple segments are a different shape): sum of active segments if any, else elapsed minus `rest`/pause (`other_39` = `EXERCISE_SEGMENT_TYPE_PAUSE`). A session's `end - start` is elapsed time: Anton's Fitbit run was 57:19 elapsed, 27:31 running.
- ⚠️ The SDK reads each `DistanceRecord` twice (as `distanceWalkingRunning` AND `distanceCycling`), so never add distance series together — take the largest per-series total. The workout and its records sit on **different `data_source` rows** (the session has a `device_model`, the records don't): match on `(user_id, provider, source)`, not the id. `scripts/data_migrations/backfill_health_connect_workout_totals.py` does this for stored workouts (NULL-only, turns the bogus 0 kcal into NULL, idempotent).
- ⚠️ **The native Android SDK requests Health Connect permissions ONLY for the type ids Dart passes** (`mapToRecordClass(typeId)` → `getReadPermission`); asking for `workout` does not pull in the permissions its session aggregates need, and a missing one just logs "skipping … aggregates" and drops that stat. Plugin 0.0.23 had no Dart value for `totalCaloriesBurned` (so workout calories could never arrive) and sent cadence as `cyclingCadence` (the HealthKit name) which Android did not map; the SDK manifest also lacked READ_POWER/SPEED/TOTAL_CALORIES_BURNED/CYCLING_PEDALING_CADENCE. Fixed in axlbrains forks that axl-app pins since 2026-09-19 — plugin `axlbrains/open_wearables_health_sdk@e9773df` (branch `axl/0.0.23-hc`), Android `axlbrains/open_wearables_android_sdk` tag `v0.12.0-axl.1` (jitpack) — and upstreamed as the-momentum/open_wearables_android_sdk#33 + open_wearables_health_sdk#59. Do NOT "fix" cadence by changing the Dart id: iOS's rawValue is `cyclingCadence`; the Android side takes it as an alias.
- **iOS token refresh (OW #34):** upstream iOS SDK 0.15.0 ships `configure(host:, tokenRefreshURL:)` natively (same shape as our `feat/configurable-token-refresh-endpoint`, now superseded); axl-app passes it on plugin 0.0.23 since 2026-09-19 with our iOS fork `fix/healthkit-authorization-dialog@ba6203f` rebased onto 0.15.0. Only the on-device proof is left — baseline 2026-09-19 was 28 `sdk_auth_reject reason=expired` / 55 accepted batches from 3 users per 24h; success = every `expired` followed by an accepted batch from the same user.

## ⚠️ Observability gotchas (cost us long debugs)

- **⚠️⚠️ THE REAL reason prod tracebacks were invisible (root-caused 2026-07-07, axl-deployment#56): a Cloud Logging EXCLUSION with a bare `httpRequest.status<400` predicate and NO presence guard silently drops ALL container logs (stdout/stderr/varlog) for the targeted services.** At exclusion-evaluation time a log entry with **no `httpRequest` field** (every app stdout line) is treated as `status=0`, and `0<400` is true → it matches → excluded. So `exclude-ow-2xx-access-logs` (`(service=api OR worker) AND httpRequest.status<400`) ate every container log for `open-wearables-prod-api`+`-worker`, leaving only request logs with `status>=400` — 5xx showed a request line but **never a traceback**. THE TRAP: a *read* filter `httpRequest.status<400` does NOT match no-httpRequest entries, so it looks innocent in Logs Explorer; it only bites at exclusion time. **Fix (applied live): pin the exclusion to the requests logName so container logs can never match** — `logName="projects/axl-platform-prod/logs/run.googleapis.com%2Frequests" AND (service=api OR worker) AND httpRequest.status<400`. Any exclusion that targets *access* logs must match `logName=".../requests"` or `httpRequest.requestUrl=~...`, never a bare status compare. The health/cron/scanner exclusions are safe because they already match on `requestUrl=~`/`status=404` (implicit presence guard).
- Logging exclusions live on the **`_Default` sink** (`gcloud logging sinks describe _Default`, NOT `gcloud logging exclusions`). To debug a "no traceback" 500: `--update-exclusion=name=<x>,disabled=true`, repro, read logs, then restore. Propagation takes a few minutes.
- **Also a cause (but NOT what hit OW api/worker — that was the exclusion above): `cpu_idle = true` (CPU throttling) on a low-traffic Cloud Run service can drop container stdout/stderr** — instance throttled to ~0 CPU before the log pipeline flushes. Set `cpu_idle = false` (`--no-cpu-throttling`, in `infra/gcp/terraform/modules/open_wearables_stack/cloud_run.tf`). NB api already had `cpu-throttling=false` while still dark, and the frontend had `cpu-throttling=true` and logged fine — so if logs are missing WITH throttling off, suspect an exclusion, not CPU.
- **Red herrings that are NOT the cause:** stdout buffering (`PYTHONUNBUFFERED` — already set); runtime SA missing `roles/logging.logWriter` (Cloud Run ships container logs via the service agent, verified `axl-av-prod` logs with no logging role); the VPC connector + `vpc-egress=private-ranges-only` (a throwaway `hello` service with the same connector logged fine); the cloudsql sidecar. Good probes: compare against a service that logs (`open-wearables-prod-frontend`, `axl-av-prod`); Cloud Run **Jobs** always have CPU so they log.
- ⚠️ **`http_request` lines with `level=error` are NOT errors by themselves.** Upstream's `app/middlewares.py` logs *every* 4xx at `level=error` (`"error" if status >= 400`), arriving with the 0.9 sync. The bulk is `POST /api/v1/sdk/users/{id}/sync` → **401 `expired`**: the SDK token is a 60-minute JWT (`access_token_expire_minutes`), the app refreshes it and re-uploads — the same users show accepted `apple_sdk_batch_received` batches alongside. Confirm with `jsonPayload.action="sdk_auth_reject"` (reason `expired`) before calling it data loss. Cloud Logging **severity** stays default, so `severity>=ERROR` queries are unaffected; only `jsonPayload.level` queries see them. Note these rejected batches never reach `apple_sdk_batch_received`, so the received-vs-imported check cannot see them — a user with 401s and *zero* accepted batches is the real signal.
- App logging: `app/utils/structured_logging.py` `log_structured()` does `print(json, file=sys.stdout, flush=True)`. `app/main.py` reconfigures root logging to stdout and adds a global `Exception` handler that logs the traceback before returning 500 (so prod 5xx are root-causable once logs flow). In prod a `UvicornAccess2xxFilter` drops happy-path 2xx access lines.
