## Upstream sync

- `.github/workflows/upstream-sync.yml` runs weekly (Mon 06:00 UTC, cron `0 6 * * 1`); GitHub delays it ~1–1.5h. The `main` leg opens a PR; the **`axl-integration` leg routinely fails on merge conflicts** and needs a manual merge — this is by design, not a regression.
- Recurring conflict file: `backend/app/repositories/event_record_detail_repository.py`. Resolution convention: **keep our `create_and_flush()` that routes through `bulk_create` (`INSERT … ON CONFLICT DO UPDATE`)** over upstream's savepoint/`IntegrityError` variant — we avoid Postgres ERROR-log noise. Drop the now-unused `IntegrityError` import if you take our side.
- **After every sync, run `alembic heads` (in `backend/`).** Upstream and our branch routinely add migrations off the same parent, leaving **two unmerged heads**. `alembic upgrade head` (what the prod init job runs) then fails with "Multiple head revisions present" and **migrations silently stop applying** — which already shipped a prod image whose code queried a column the DB never got (`provider_settings.webhook_secret`), 500ing `/connections` with no traceback (axlbrains/open-wearables#22). If >1 head: `alembic merge -m "merge heads" <rev1> <rev2>`, commit, and on prod apply the lagging branch with `alembic upgrade heads` (plural) before re-running the init job.
- **Background tasks now go through `app/integrations/task_dispatcher.py` (`dispatch_task(RegisteredTask.X, …)`), not raw Celery `.delay()`/`apply_async`.** Garmin tasks live under `app/integrations/celery/tasks/garmin/`. When a sync conflict shows local `.delay()`/`apply_async` vs the dispatcher form, **take the dispatcher side.**
- **⚠️ Recurring merge-class gotcha: upstream code assumes a real Redis; prod runs the Postgres-backed `KvStoreClient` shim (`REDIS_HOST` unset → `app/integrations/kv_store.py`).** KvStore covers GET/SET/SETEX/EXPIRE/INCR/DEL, sets, lists, pipeline/lock/scan/pubsub-stub, and now `eval` (compare-and-delete only). When upstream introduces a new Redis primitive, KvStore 500s at runtime with `AttributeError: 'KvStoreClient' object has no attribute 'X'` — invisible until that path runs (bit us: `.eval()` Lua in `sync_coordination.release_primary`, fixed 0.6.13; and the `config/.env` `REDIS_HOST=redis` bake, #33). After a sync that touches redis/coordination/rate-limit/lock code, grep the diff for `get_redis_client().<method>` and confirm KvStore implements `<method>`.

## Contributing PRs upstream

- Upstream `the-momentum` runs a `validate-pr-title` check (`amannn/action-semantic-pull-request`) that enforces a **fixed conventional-commit scope allowlist**: `backend, frontend, docs, api, mcp, auth, integrations, dashboard, settings, users`. Provider/feature names (`webhooks`, `fitbit`, `garmin`, `oura`, …) are **not** valid scopes — map them to **`integrations`** (or `backend`). A bad scope fails the check and blocks merge even on an approved PR.
- Our fork→upstream PRs run gated: their workflow runs sit at `action_required` until an upstream maintainer approves each run, so fixing a title won't flip the check green until they re-approve.

## CI / local dev

- `ci.yml` triggers **only on push to `main` and on pull_request** (paths-filtered). **Pushing to `axl-integration` does NOT run CI** — open a PR to get tests. So local pushes to the integration branch are unvalidated.
- Backend tests need **Docker** (testcontainers spin up Postgres + Redis in `conftest.py`); they can't run in a Docker-less sandbox. CI provides Postgres as a service + env (`ENV=test`, `SECRET_KEY`, base64 `MASTER_KEY`).
- No `uv` preinstalled in some envs: `pip install --user uv` then `uv sync`. To import the app / run non-DB tests locally set `ENV=test SECRET_KEY=… MASTER_KEY=<base64>`.

## Prod infra (GCP project `axl-platform-prod`, region `europe-west1`)

- Cloud Run services: `open-wearables-prod-api`, `open-wearables-prod-worker`; job `open-wearables-prod-init`. Image repo: `europe-west1-docker.pkg.dev/axl-platform-prod/open-wearables-prod/backend:<semver>`.
- **There are NO Cloud Build triggers.** Prod images are built + deployed manually with semver tags (the `SHORT_SHA` flow in `backend/cloudbuild.yaml` is unused for prod). Release recipe:
  1. `gcloud builds submit backend --config <cfg> ...` building with `--build-arg APP_VERSION=<ver>` (bakes the real version into the image).
  2. `gcloud run services update {open-wearables-prod-api,open-wearables-prod-worker} --image …:<ver>` and `gcloud run jobs update open-wearables-prod-init --image …:<ver>`.
- **⚠️ Terraform & the `TFVARS_PROD` secret (source of truth for prod).** `.github/workflows/terraform-deploy.yml` runs `terraform apply` on every **push to `axl-integration`/`main` touching `infra/gcp/terraform/**`** (and `plan` on PRs; auth `github-terraform@`). It **overwrites** the local `environments/prod/terraform.tfvars` with the `TFVARS_PROD` repo secret (`printf '%s' "$TFVARS_PROD" > terraform.tfvars`). So **the secret — NOT module-variable defaults — is what applies to prod.**
- **Editing the secret (process proven 2026-07-15):** the gitignored local `environments/prod/terraform.tfvars` is the maintained **mirror** of the secret. Edit the file, then `gh secret set TFVARS_PROD --repo axlbrains/open-wearables < infra/gcp/terraform/environments/prod/terraform.tfvars` — **repo admin rights suffice** (the old "org owner only" note was wrong; the `slavarosin` gh token has admin). Secrets are write-only — you can't read back the old value, so **ALWAYS plan-gate before any apply**: rerun the terraform workflow on a PR touching `infra/**` (`gh run rerun <run-id>`) and read the plan in the logs. ⚠️ The mirror GOES STALE: on 2026-07-15 it still had the pre-#22 broken worker command (`/root_project/.venv/...`), the `cloud-run-api.sh` api command (live uses the `/opt/venv/bin/python -m fastapi` override), and **no `cloud_sql_tier`** (root default `db-f1-micro` would have DOWNGRADED the live `db-custom-1-3840` DB). The plan-gate caught all three; a healthy plan shows only no-ops (dropping `client`/`client_version` fields, vpc-connector short→full name on the init job).
- **A tfvars var only takes effect if the prod ROOT module declares + passes it through** (`environments/prod/variables.tf` + `main.tf`). `backend_worker_resource_limits` was missing until 2026-07-15 (added in PR #35's branch); check pass-through before adding new vars to the secret.
- **Image reverts are now MITIGATED (was: "terraform clobbers the manual image").** Every prod service+job — `backend_api`, `backend_worker`, `backend_init`, and `frontend` (the last added 2026-07-09, it was the one still exposed) — has `lifecycle { ignore_changes = [template[0].containers[0].image] }`, so an apply no longer rolls the running image back to the stale `var.backend_image`/`var.frontend_image` pin in the secret. You can push infra changes without re-deploying the image afterward. (Scaling, env, ingress etc. are NOT in `ignore_changes` — those still reconcile to the secret on apply.)
- **Scaling (OW#32): DONE 2026-07-15.** min=1 everywhere is codified: PR #35 merged, `TFVARS_PROD` sets all three `*_min_instances = 1`, apply ran clean (only no-ops). Frontend image now also has `ignore_changes`.
- **`INGEST_WORKOUT_SAMPLES=true` (Strava per-sample streams): codified 2026-07-15** in `TFVARS_PROD` `backend_api_env`+`backend_worker_env`. First real ingestion (24 workouts, 2026-07-14 20:00 sync) **OOMed the worker at 1Gi** (3×503, self-healed via Cloud Tasks retries) → worker memory is **2Gi**, codified via `backend_worker_resource_limits` in the secret + root pass-through. Note: `_ingest_workout_streams` has no skip-if-samples-exist — re-fetch only happens if a sync window re-covers old workouts (hourly windows don't in practice); upstream PR candidate.
- `GET /health` → `{"status":"ok","version":"<ver>"}`; version comes from `APP_VERSION` build arg → ENV → `settings.app_version`, and also feeds FastAPI `info.version` (fixes the stale `0.1.0` in `/openapi.json`). Consumed by `status.axl.coach`'s `wearables-sync` tile.
- **Public domains:** api = `ow-api.axl.coach`, dashboard = `ow-dashboard.axl.coach` (Cloud Run domain-mappings). The **worker is `internal` ingress by design** (Cloud Tasks HTTP dispatch target — external curl gets a Google 404, that's correct). api + frontend must be `ingress=all`; if either shows a Google-level 404 externally, ingress has **drifted to `internal`** — restore with `gcloud run services update <svc> --ingress=all`.

"Turn OW back on" = `gcloud sql instances patch open-wearables-prod-db --activation-policy=ALWAYS` (takes ~1-2 min to reach `RUNNABLE`).
- **Version bumps need `uv lock`.** `uv.lock` pins the project's own version; bump `backend/pyproject.toml` then run `uv lock` (or `uv sync --locked` / the Docker build fails with "lockfile needs to be updated"). Prod fork line is currently **0.7.x** — backend 0.7.0 (2026-07-13 upstream sync), frontend 0.7.1 (2026-07-14, #37 405-guard + Nitro error-hook) — independent, ahead of upstream; see fork-layout section.
- **⚠️ NEVER let `backend/config/.env` reach the build context.** It's a gitignored local docker-compose dev file (`REDIS_HOST=redis`, `DB_HOST=db`, …). The Dockerfile does `COPY . .`, and `gcloud builds submit` respects `.gcloudignore` (NOT `.gitignore`), so a build from your local working dir bakes `config/.env` into the image at `/root_project/config/.env`. pydantic reads it at runtime, and **any key the Cloud Run env doesn't explicitly set is NOT overridden** — so the baked `REDIS_HOST=redis` won `settings.redis_host`, flipped `_redis_configured()` True, and every OAuth `/authorize` 500'd trying to reach `redis:6379` (unresolvable in Cloud Run) while `/health`+`/providers` stayed green (they never touch redis/kv). This shipped the 0.6.11 prod outage (axlbrains/open-wearables#33). DB creds survived only because Cloud Run env sets `DB_*` explicitly. **Fix is in `backend/.dockerignore` + `backend/.gcloudignore`: both now exclude `.env` / `**/.env` (keep `.env.example`).** Prod intentionally runs with NO Redis (`redis_host` default `localhost` → Postgres-backed `KvStoreClient`); do not set `REDIS_HOST` in prod. Quick live mitigation if it ever recurs before a rebuild: `gcloud run services update {api,worker} --update-env-vars REDIS_HOST=localhost` (env wins over the baked `.env`).
- **Prod build configs (semver, not the SHORT_SHA `cloudbuild.yaml`):** write a throwaway config that builds+pushes only. Backend: `--build-arg APP_VERSION=<ver>`, `-t …/backend:<ver>`, submit `gcloud builds submit backend --config <cfg>`. Frontend (TanStack Start SSR on a **Nitro v3 server**, not a static SPA; bakes API URL at **build time**): `--build-arg VITE_API_URL=https://ow-api.axl.coach`, `-t …/frontend:<ver>`, submit `gcloud builds submit frontend --config <cfg>`. Frontend gotchas (2026-07-14, #37): server-side code lives in `frontend/server/{middleware,plugins}/` and is only picked up because `serverDir: 'server'` is set in the vite `nitro({...})` options; `method-guard.ts` 405s all non-GET/HEAD before SSR and `log-errors.ts` logs unhandled errors to stderr — keep both. Local prod builds need `NODE_ENV=production` at build time (Dockerfile sets it) or SSR 500s on the dev jsx-runtime. Use `options.logging: GCS_ONLY` (the build SA lacks `logging.logWriter`, so `CLOUD_LOGGING_ONLY` hides the build log). Then `gcloud run services update {api,worker,frontend} --image …:<ver>` and `gcloud run jobs update open-wearables-prod-init --image …:<ver>`.
- **⚠️ init-job gotchas (root of the #22 "migrations silently don't apply" saga — fixed 2026-07-06, tracked in [axl-deployment#55](https://github.com/axlbrains/axl-deployment/issues/55)):** (1) the `scripts/start/cloud-run-*.sh` scripts historically referenced `/root_project/.venv` but the Dockerfile builds the venv at **`/opt/venv`** — api/worker only survived because their Cloud Run **command is overridden** to `/opt/venv/bin/python`; the init JOB runs `cloud-run-init.sh` directly, so alembic+seeds silently failed on a nonexistent path. ## Strava API is subscriber-only (owner, not athletes)

- Strava is moving **Standard Tier** API access to subscriber-only (deadline **June 30, 2026**). The subscription is required on the **API-application OWNER's Strava account** (the one behind our `strava_client_id`), **NOT** on the end athletes. If the owner already subscribes there's no extra cost; active devs get 3 months free. When the app is unsubscribed it goes **`Inactive`** and `GET /api/v3/push_subscriptions` returns `Forbidden / Application Status Inactive` — webhooks AND REST are dead until the owner subscribes. Alternative: **Extended Access Tier** (no subscription, higher rate/user limits, by application — for larger partners). Reactivation is a product action on our side (subscribe on the owner account), not a code change.

## ⚠️ Observability gotchas (cost us long debugs)

- **⚠️⚠️ THE REAL reason prod tracebacks were invisible (root-caused 2026-07-07, axl-deployment#56): a Cloud Logging EXCLUSION with a bare `httpRequest.status<400` predicate and NO presence guard silently drops ALL container logs (stdout/stderr/varlog) for the targeted services.** At exclusion-evaluation time a log entry with **no `httpRequest` field** (every app stdout line) is treated as `status=0`, and `0<400` is true → it matches → excluded. So `exclude-ow-2xx-access-logs` (`(service=api OR worker) AND httpRequest.status<400`) ate every container log for `open-wearables-prod-api`+`-worker`, leaving only request logs with `status>=400` — 5xx showed a request line but **never a traceback**. THE TRAP: a *read* filter `httpRequest.status<400` does NOT match no-httpRequest entries, so it looks innocent in Logs Explorer; it only bites at exclusion time. **Fix (applied live): pin the exclusion to the requests logName so container logs can never match** — `logName="projects/axl-platform-prod/logs/run.googleapis.com%2Frequests" AND (service=api OR worker) AND httpRequest.status<400`. Any exclusion that targets *access* logs must match `logName=".../requests"` or `httpRequest.requestUrl=~...`, never a bare status compare. The health/cron/scanner exclusions are safe because they already match on `requestUrl=~`/`status=404` (implicit presence guard).
- Logging exclusions live on the **`_Default` sink** (`gcloud logging sinks describe _Default`, NOT `gcloud logging exclusions`). To debug a "no traceback" 500: `--update-exclusion=name=<x>,disabled=true`, repro, read logs, then restore. Propagation takes a few minutes.
- **Also a cause (but NOT what hit OW api/worker — that was the exclusion above): `cpu_idle = true` (CPU throttling) on a low-traffic Cloud Run service can drop container stdout/stderr** — instance throttled to ~0 CPU before the log pipeline flushes. Set `cpu_idle = false` (`--no-cpu-throttling`, in `infra/gcp/terraform/modules/open_wearables_stack/cloud_run.tf`). NB api already had `cpu-throttling=false` while still dark, and the frontend had `cpu-throttling=true` and logged fine — so if logs are missing WITH throttling off, suspect an exclusion, not CPU.
- **Red herrings that are NOT the cause:** stdout buffering (`PYTHONUNBUFFERED` — already set); runtime SA missing `roles/logging.logWriter` (Cloud Run ships container logs via the service agent, verified `axl-av-prod` logs with no logging role); the VPC connector + `vpc-egress=private-ranges-only` (a throwaway `hello` service with the same connector logged fine); the cloudsql sidecar. Good probes: compare against a service that logs (`open-wearables-prod-frontend`, `axl-av-prod`); Cloud Run **Jobs** always have CPU so they log.
- App logging: `app/utils/structured_logging.py` `log_structured()` does `print(json, file=sys.stdout, flush=True)`. `app/main.py` reconfigures root logging to stdout and adds a global `Exception` handler that logs the traceback before returning 500 (so prod 5xx are root-causable once logs flow). In prod a `UvicornAccess2xxFilter` drops happy-path 2xx access lines.
