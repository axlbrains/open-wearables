## Upstream sync

- `.github/workflows/upstream-sync.yml` runs weekly (Mon 06:00 UTC, cron `0 6 * * 1`); GitHub delays it ~1–1.5h. The `main` leg opens a PR; the **`axl-integration` leg routinely fails on merge conflicts** and needs a manual merge — this is by design, not a regression.
- Recurring conflict file: `backend/app/repositories/event_record_detail_repository.py`. Resolution convention: **keep our `create_and_flush()` that routes through `bulk_create` (`INSERT … ON CONFLICT DO UPDATE`)** over upstream's savepoint/`IntegrityError` variant — we avoid Postgres ERROR-log noise. Drop the now-unused `IntegrityError` import if you take our side. Applied again in the 2026-08-15 sync (upstream **dropped the `event_record_detail` base table** — details live in the concrete `workout_details`/`sleep_details`/… tables now); also take upstream's `bulk_create` docstring side (no hardcoded `("workout","sleep")` check — `DETAIL_MODELS.get` below already rejects unknown types).
- **After every sync, run `alembic heads` (in `backend/`).** Upstream and our branch routinely add migrations off the same parent, leaving **two unmerged heads**. `alembic upgrade head` (what the prod init job runs) then fails with "Multiple head revisions present" and **migrations silently stop applying** — which already shipped a prod image whose code queried a column the DB never got (`provider_settings.webhook_secret`), 500ing `/connections` with no traceback (axlbrains/open-wearables#22). If >1 head: `alembic merge -m "merge heads" <rev1> <rev2>`, commit, and on prod apply the lagging branch with `alembic upgrade heads` (plural) before re-running the init job.
- 2026-09-07 sync (52 commits, upstream 0.7.x line): same `event_record_detail` resolution; upstream introduced SDK payload S3 offload (`payload_ref`) and XML multipart client-completion — both dispatches converted to `dispatch_task` (new `COMPLETE_AND_PROCESS_AWS_UPLOAD`), `worker.sh` took upstream's io+cpu split (new `xml_sync` queue) with `/opt/venv/bin` paths, `cloud-run-init.sh` gained upstream's new init steps (`seed_archival_settings` + ultrahuman/whoop data migrations), and upstream tests that mock `.delay` / expect 404-on-purge / expect stale-row-on-duplicate were adapted to fork semantics (dispatcher mocks, idempotent DELETE, upsert refreshes fields).
- **Background tasks now go through `app/integrations/task_dispatcher.py` (`dispatch_task(RegisteredTask.X, …)`), not raw Celery `.delay()`/`apply_async`.** Garmin tasks live under `app/integrations/celery/tasks/garmin/`. When a sync conflict shows local `.delay()`/`apply_async` vs the dispatcher form, **take the dispatcher side.**
- **⚠️ Recurring merge-class gotcha: upstream code assumes a real Redis; prod runs the Postgres-backed `KvStoreClient` shim (`REDIS_HOST` unset → `app/integrations/kv_store.py`).** KvStore covers GET/SET(nx/ex)/SETEX/EXPIRE/INCR/DEL/EXISTS, sets, lists, pipeline/lock/scan/pubsub-stub, and `eval` (compare-and-delete only). When upstream introduces a new Redis primitive, KvStore 500s at runtime with `AttributeError: 'KvStoreClient' object has no attribute 'X'` — invisible until that path runs (bit us: `.eval()` Lua in `sync_coordination.release_primary`, fixed 0.6.13; the `config/.env` `REDIS_HOST=redis` bake, #33; and `.exists()` in upstream's `dashboard_stats_cache` — caught pre-deploy in the 2026-08-15 sync, `exists` added to KvStore). After a sync that touches redis/coordination/rate-limit/lock code, grep the diff for `get_redis_client().<method>` and confirm KvStore implements `<method>` — **including the kwargs**: 0.8.0 shipped two signature mismatches that method-name checks missed (`lock(sleep=...)` — upstream's token-refresh guard, TypeError'd Strava sync until 0.8.2 added blocking acquisition; and the fork's `@idempotent` key fn lagging a task's new `payload_ref` param, which broke every SDK upload until 0.8.1).

## Contributing PRs upstream

- Upstream `the-momentum` runs a `validate-pr-title` check (`amannn/action-semantic-pull-request`) that enforces a **fixed conventional-commit scope allowlist**: `backend, frontend, docs, api, mcp, auth, integrations, dashboard, settings, users`. ## "Someone else's no-data is not our error" — the recurring noise class

Three prod incidents in two days, all the same shape: a provider says "nothing here" in a way that looks like a failure, we report it, and a retry loop keeps re-reporting it forever.

- **Polar 401 on optional endpoints** (0.8.5): Elixir/SleepWise/daily-activity are gated per user, device and consent — one athlete 401s while another gets data on the same endpoint with a healthy token. `Polar247Data.CORE_ENDPOINT_PREFIXES` now draws the line at the product dependency: sleep (`/v3/users/sleep/`, trailing slash matters — `sleep-skin-temperature` is NOT core) and `/v3/exercises` stay loud, everything else logs `polar_endpoint_not_permitted` and returns no data. A dead token still screams, because it 401s on the core endpoints too. Took three deploys (0.8.3→0.8.5) because each wrong guess only showed up on a live sync, not in tests.
- **Strava 404 on `/streams`** (0.8.7): manual activities have no streams. `_ingest_workout_streams` now returns `None` for that — distinct from `0` ("streams exist but weren't ready"), so the webhook path also stops scheduling delayed retries for an activity that will never have samples. One hand-logged gym session was producing a traceback plus a Sentry event twice an hour, forever, because the 6h lookback re-covers it and the skip-if-samples-exist guard can never be satisfied.
- Rule of thumb when adding a provider path: before wrapping an exception in `log_and_capture_error`, ask whether that status can mean "this user/activity legitimately has no such data". If yes, it needs its own quiet branch.

## ⚠️ Large SDK batches take a different code path (and it broke silently)

- The dispatcher offloads any payload over `task_payload_inline_max_bytes` (256 KB) to task-payload storage and swaps the task for its `*_reference` variant, forwarding **every other kwarg verbatim** — see `_OFFLOAD_MAP` in `task_dispatcher.py`. So a reference task's signature must stay a superset of its base task's.
- 2026-09-07 upstream added `payload_ref` to `process_sdk_upload`; the reference sibling wasn't updated, and **19 Apple SDK batches were accepted with 202 and then dropped** after Cloud Tasks exhausted 160 retries. Raw payload archival is off in prod (`raw_payload_storage=disabled`), so they were unrecoverable server-side — the data needs a re-export from the device. Fixed in 0.8.3, plus `TestReferenceTaskSignatureParity` so the drift fails in CI instead of in prod.
- **How to detect silent batch loss**: compare `apple_sdk_batch_received` (api) against `apple_sdk_import_complete` (worker) by `batch_id` over a window. Both carry `batch_id`, and a received batch with no completion never reached the worker. Healthy looks like 18 received / 18 imported.

## One live connection per provider account (fork divergence, 2026-09-08)

- `settings.single_active_connection_per_provider_account` (default **true** here): connecting a provider account to a profile revokes that same account's connections on every other profile, in both the OAuth (`BaseOAuthTemplate._revoke_superseded_connections`) and API-key (Hevy) flows, emitting `connection.revoked` with reason `superseded_by_new_connection`.
- Upstream instead treats a shared provider account as a feature and fans synced data out to every profile holding it (`sync_vendor_data_task`); set the flag false to get that back. That fan-out is what masked a real problem: one athlete had two OW profiles on the same Polar account, re-authorising killed the older token at Polar, and the stale row 401'd hourly with nothing to clear it.
- ⚠️ **`DELETE /users/{id}/connections/{provider}` calls the provider's deregistration API.** For Polar that is `DELETE /v3/users/{provider_user_id}`, which unregisters the *athlete*, not the connection — dangerous when two profiles share the account. When cleaning up a duplicate, change `status` directly instead. For Strava it is `POST /oauth/revoke` on that connection's own token, which is safe.
- ⚠️ **axl-api does not handle `connection.revoked`** (only `connection.created`), so disconnects don't reach it and its state drifts — tracked in [axl-api#297](https://github.com/axlbrains/axl-api/issues/297).

## Late-arriving provider data — the recurring race class

Two prod bugs of the same shape: data that becomes available *after* its dated sync window has passed is never fetched again.
- **Strava streams** (fixed 0.7.2): webhook precedes stream processing → delayed retry task; see Strava section above.
- **Polar sleep** (fixed 0.8.0, 2026-09-07): nights enter `/v3/users/sleep/available` only after the watch syncs with Polar Flow — days late for infrequent syncers. `get_sleep_data` intersected available nights with the hourly window, so late nights were lost (Jevgeni had zero polar sleep since June). Now it also fetches any available night within Polar's 28-day retention that isn't stored yet — existence probe `event_record_service.get_sleep_end_dates` filters by **`DataSource.provider`** (`source` is empty for pull-ingested polar rows — filtering on it re-fetched everything hourly and hit an FK violation on scores, 0.8.1). Both polar save paths now re-point the health score at the record `create_or_merge_sleep` actually returned (merge discards the pre-generated id).
- When adding a provider, ask: does the API list data by *availability* or by *date*? If availability lags, don't intersect with the sync window.

## Strava API is subscriber-only (owner, not athletes)

- Strava is moving **Standard Tier** API access to subscriber-only (deadline **June 30, 2026**). The subscription is required on the **API-application OWNER's Strava account** (the one behind our `strava_client_id`), **NOT** on the end athletes. If the owner already subscribes there's no extra cost; active devs get 3 months free. When the app is unsubscribed it goes **`Inactive`** and `GET /api/v3/push_subscriptions` returns `Forbidden / Application Status Inactive` — webhooks AND REST are dead until the owner subscribes. Alternative: **Extended Access Tier** (no subscription, higher rate/user limits, by application — for larger partners). Reactivation is a product action on our side (subscribe on the owner account), not a code change.

## ⚠️ Observability gotchas (cost us long debugs)

- **⚠️⚠️ THE REAL reason prod tracebacks were invisible (root-caused 2026-07-07, axl-deployment#56): a Cloud Logging EXCLUSION with a bare `httpRequest.status<400` predicate and NO presence guard silently drops ALL container logs (stdout/stderr/varlog) for the targeted services.** At exclusion-evaluation time a log entry with **no `httpRequest` field** (every app stdout line) is treated as `status=0`, and `0<400` is true → it matches → excluded. So `exclude-ow-2xx-access-logs` (`(service=api OR worker) AND httpRequest.status<400`) ate every container log for `open-wearables-prod-api`+`-worker`, leaving only request logs with `status>=400` — 5xx showed a request line but **never a traceback**. THE TRAP: a *read* filter `httpRequest.status<400` does NOT match no-httpRequest entries, so it looks innocent in Logs Explorer; it only bites at exclusion time. **Fix (applied live): pin the exclusion to the requests logName so container logs can never match** — `logName="projects/axl-platform-prod/logs/run.googleapis.com%2Frequests" AND (service=api OR worker) AND httpRequest.status<400`. Any exclusion that targets *access* logs must match `logName=".../requests"` or `httpRequest.requestUrl=~...`, never a bare status compare. The health/cron/scanner exclusions are safe because they already match on `requestUrl=~`/`status=404` (implicit presence guard).
- Logging exclusions live on the **`_Default` sink** (`gcloud logging sinks describe _Default`, NOT `gcloud logging exclusions`). To debug a "no traceback" 500: `--update-exclusion=name=<x>,disabled=true`, repro, read logs, then restore. Propagation takes a few minutes.
- **Also a cause (but NOT what hit OW api/worker — that was the exclusion above): `cpu_idle = true` (CPU throttling) on a low-traffic Cloud Run service can drop container stdout/stderr** — instance throttled to ~0 CPU before the log pipeline flushes. Set `cpu_idle = false` (`--no-cpu-throttling`, in `infra/gcp/terraform/modules/open_wearables_stack/cloud_run.tf`). NB api already had `cpu-throttling=false` while still dark, and the frontend had `cpu-throttling=true` and logged fine — so if logs are missing WITH throttling off, suspect an exclusion, not CPU.
- **Red herrings that are NOT the cause:** stdout buffering (`PYTHONUNBUFFERED` — already set); runtime SA missing `roles/logging.logWriter` (Cloud Run ships container logs via the service agent, verified `axl-av-prod` logs with no logging role); the VPC connector + `vpc-egress=private-ranges-only` (a throwaway `hello` service with the same connector logged fine); the cloudsql sidecar. Good probes: compare against a service that logs (`open-wearables-prod-frontend`, `axl-av-prod`); Cloud Run **Jobs** always have CPU so they log.
- App logging: `app/utils/structured_logging.py` `log_structured()` does `print(json, file=sys.stdout, flush=True)`. `app/main.py` reconfigures root logging to stdout and adds a global `Exception` handler that logs the traceback before returning 500 (so prod 5xx are root-causable once logs flow). In prod a `UvicornAccess2xxFilter` drops happy-path 2xx access lines.
